# 배포 전 검증

## 왜 필요한가

원본 대화에서 결과가 좋았던 이유가 프롬프트 때문인지, 그 대화에 깔려 있던 맥락 때문인지는 구분되지 않는다. 앞선 대화에서 이미 자료를 올렸거나 조건을 설명했다면, 프롬프트는 그 부분을 생략한 채로도 잘 작동한 것처럼 보인다. 받는 사람 쪽에는 그 맥락이 없다.

그래서 검증은 **맥락을 지운 상태**에서 해야 한다.

## 절차

1. **새 대화를 연다.** 이전 대화, 첨부 파일, 프로젝트 지침을 쓰지 않는다.
2. 만든 프롬프트만 붙여넣고 결과를 받는다.
3. 문서의 "확인 항목"과 하나씩 대조한다.
4. 변수를 **다른 값**으로 바꿔 한 번 더 돌린다. 주제가 달라져도 형식이 유지돼야 배포할 수 있다.
5. 가능하면 다른 AI 서비스에서 한 번 더 돌린다. 도구 무관 배포가 목표라면 이 시험이 있어야 안전하다.

세 번 중 두 번 이상 통과하지 못하면 배포하지 않고 프롬프트를 고친다.

## 판정 기준을 잡는 법

같은 프롬프트라도 AI는 매번 똑같은 문장을 내놓지 않는다. 그래서 기준은 "글자가 같은가"가 아니라 **"형식과 요건을 지켰는가"**로 잡는다.

- 판정 가능: 절 개수, 표 열 수, 분량 범위, 지정 항목 포함 여부, 금지어 미사용
- 판정 곤란: 완성도, 자연스러움, 설득력

판정 곤란한 항목만 남아 있다면 합격 기준이 아직 덜 정리된 것이다. 기록지 4)로 돌아간다.

## 실패했을 때 어디를 고치나

| 증상 | 고칠 블록 |
| --- | --- |
| 엉뚱한 종류의 결과가 나옴 | [역할], [목표] |
| 방향은 맞는데 단계를 건너뜀 | [수행 절차] — 단계를 쪼개거나 순서를 명시 |
| 분량·구조가 매번 다름 | [출력 형식] — 수치로 못 박기 |
| 같은 실수가 반복됨 | [제약] — 금지와 대체 행동을 짝으로 |
| 사람마다 결과 편차가 큼 | [입력값] — 변수 설명과 예시 보강 |
| 특정 서비스에서만 실패 | 범용화 누락. 도구 종속 표현 재점검 |

## 고친 뒤에는

버전 번호를 올리고 무엇을 왜 고쳤는지 한 줄로 남긴다.

```
v2 (날짜): 표 열 수가 매번 달라져 [출력 형식]에 "3열 고정" 추가
```

이미 배포한 판을 덮어쓰지 않는다. 수업에서 나눠 준 판과 지금 판이 다르면, 질문을 받았을 때 어느 쪽 이야기인지부터 확인해야 한다.

## 배포 후 챙길 것

- 받는 사람이 어디서 막혔는지 한 가지만 물어 둔다. 그것이 다음 판의 [제약]이 된다.
- 같은 질문이 세 번 넘게 나오면 프롬프트가 아니라 사용 안내를 고친다.
