# 세션 로그 → 배포용 프롬프트

## 이 스킬이 하는 일

잘 풀린 작업 하나를 골라, 그 과정을 **다른 사람이 복사·붙여넣기만 하면 같은 결과를 얻는 프롬프트 한 벌**로 바꾼다. 산출물은 `.md` 파일 하나다.

로그를 요약하는 작업이 아니다. 로그는 재료일 뿐이고, 목표는 **재현 가능한 지시문**이다. 두 가지를 구분하지 못하면 "무슨 작업을 했는지 설명하는 문서"가 나오는데, 그건 붙여넣어도 작동하지 않는다.

## 모드 판별

가장 먼저 로그가 어디 있는지 정한다.

| 상황 | 모드 | 처리 |
| --- | --- | --- |
| 지금 진행 중인 이 대화가 원본 | A. 회고 추출 | 대화 이력을 직접 훑어 1단계로 |
| 로그·기록지를 텍스트로 붙여 줌 | B. 변환 | 붙여넣은 내용만 근거로 1단계로 |
| 로그 파일을 첨부함 | B. 변환 | 파일을 읽고 1단계로 |
| 로그가 여러 건 | C. 분할 | 작업 단위로 쪼개 각각 파일 하나씩 |

모드 A에는 함정이 하나 있다. 이 대화에 이미 나온 정보를 "말 안 해도 아는 것"으로 여겨 프롬프트에서 빠뜨리기 쉽다. 그래서 A에서는 조립을 마친 뒤 **"이 대화를 처음 보는 사람도 이 프롬프트만으로 실행할 수 있는가"**를 한 번 더 훑는다. 빠진 값은 입력값 블록으로 올린다.

## 0단계: 대상 작업 확정

로그 하나에 작업이 여러 개 섞여 있으면 프롬프트가 뭉개진다. 시작 전에 확인한다.

- 로그에서 완결된 작업이 하나뿐이면 그대로 진행한다.
- 둘 이상이면 후보를 목록으로 보여 주고 어느 것을 프롬프트로 만들지 묻는다.
- 결과가 합격이었는지 로그에 근거가 없으면 무엇을 기준으로 합격이라 보는지 묻는다.

## 1단계: 기록지 5칸 추출

로그에서 아래 다섯 가지만 뽑는다. 자세한 판정 기준은 `references/extraction-rules.md`를 읽는다.

1. **최초 지시** — 작업을 처음 시킨 발화. 요약하지 말고 원문 그대로.
2. **중간 수정 지시** — 결과를 보고 고쳐 달라고 한 발화들. 시간순.
3. **통하지 않은 지시** — 기대와 어긋난 결과가 나온 지시와 어긋난 점.
4. **합격 기준** — 최종 결과를 받아들인 이유. 확인 가능한 형태로만.
5. **매번 바뀐 값** — 주제·대상·분량·파일명처럼 사람이 갈아 끼운 값.

이때 **누가 낸 의견인지 반드시 구분한다.** 어시스턴트가 먼저 제안하고 사용자가 받아들인 항목은 사용자가 처음부터 요구한 항목과 무게가 다르다. 전자는 프롬프트에 고정값으로 박고, 후자는 입력값이나 제약으로 올린다. 헷갈리면 사용자에게 묻는다.

## 2단계: 범용화

특정 서비스에서만 되는 표현이 남으면 배포처에서 그대로 실패한다. 치환 규칙은 `references/extraction-rules.md`의 범용화 표를 따른다. 핵심은 네 가지다.

- 파일 경로·업로드 전제 → "아래에 내용을 붙여넣는다"
- 스킬·확장 기능 호출 → 그 기능이 하던 일을 문장으로 풀어 쓴 절차
- 웹 검색·코드 실행 전제 → "확인이 어려우면 불확실하다고 표시하라"
- 이전 대화 참조("아까 그거") → 값을 프롬프트 안에 직접 적기

## 3단계: 여섯 블록으로 조립

프롬프트 본문은 항상 이 순서로 쓴다. 순서를 고정해야 받는 사람이 고칠 자리를 빨리 찾는다.

```
[역할] 너는 (분야)를 다루는 (역할)이다.

[목표] (완성했을 때 손에 남는 결과물 한 문장)

[입력값]
- 항목1: {여기에 채우기}
- 항목2: {여기에 채우기}

[수행 절차]
1. (첫 단계)
2. (둘째 단계)

[출력 형식]
- (분량, 구조, 표·목록 여부)

[제약]
- (하지 말 것 + 대신 할 것)
```

기록지에서 이렇게 옮긴다.

| 블록 | 재료 |
| --- | --- |
| 역할·목표 | 1) 최초 지시 |
| 수행 절차 | 2) 중간 수정 지시를 시간순 정리 |
| 출력 형식 | 4) 합격 기준 |
| 제약 | 3) 통하지 않은 지시 |
| 입력값 | 5) 매번 바뀐 값 |

### 입력값을 사람이 채우지 않고 물어보게 할 때

받는 사람이 `{ }` 자리를 직접 지우고 채우는 대신, 프롬프트를 붙여 넣으면 AI가 값을 물어보게 만들 수 있다. 이때는 `[입력값]` 블록을 `[입력 받기]` 블록으로 갈아 끼우고, 물어볼 항목을 번호 목록으로 적는다. 항목마다 무엇을 적는 자리인지 한 줄 설명과 예시 하나를 붙이게 지시한다.

**한 항목씩 묻게 하려면 "한 항목씩 묻는다"만 적어서는 모자란다.** 이 문장만 있으면 대부분의 모델이 항목을 번호로 나열한 한 메시지를 보내고 만다. 아래 두 문장을 함께 박는다.

1. **답을 받은 뒤에 다음 항목을 묻는다** — 순서를 못 박는 문장이다. 이 문장이 빠지면 "한 항목씩"이 나열 형식으로만 지켜진다.
2. **여러 항목을 한 메시지에 묶어 묻지 않는다** — 1번을 어겼을 때를 금지로 한 번 더 막는다.

마지막 항목의 답을 받기 전에는 본 작업을 시작하지 않는다는 문장을 `[수행 절차]` 첫 단계에 함께 적는다. 이 문장이 없으면 항목 두세 개만 받고 앞질러 결과를 만드는 일이 생긴다.

`[제약]`에 "정보가 부족해도 초안을 먼저 낸다" 같은 문장이 남아 있으면 물어보는 동작과 맞부딪힌다. 물어보게 바꾼 프롬프트에서는 그 문장을 지우고 "묻기 전에 먼저 만들지 않는다"로 바꾼다.

### 조립할 때 지킬 것

- 변수는 `{중괄호}`로 비운다. 예시 값은 본문이 아니라 변수표에 적는다.
- "상황에 맞게 조정하라" 같은 모호한 지시를 넣지 않는다. 판단 기준을 수치나 조건으로 적는다.
- 금지 항목은 "하지 말 것"만 적지 말고 "대신 무엇을 할지"를 함께 적는다.
- 로그에 없는 요구사항을 새로 만들어 넣지 않는다. 필요해 보이면 사용자에게 확인한다.

## 4단계: .md 파일로 저장

산출 파일 구조는 `references/output-template.md`의 틀을 그대로 따른다. 네 덩어리다.

1. 사용 안내 세 줄 (무엇을 채우고, 무엇을 붙여넣고, 결과를 어떻게 확인하는지)
2. 프롬프트 전문 (코드블록 하나에 통째로, 잘라 쓰지 않는다)
3. 변수표 (변수명 / 설명 / 예시 값)
4. 확인 항목 (받는 사람이 결과를 검사할 기준)

파일명은 `prompt-<작업슬러그>-v1.md`로 짓는다. 같은 작업을 고칠 때는 번호만 올린다.

산출물에는 색상·굵기 지정 같은 시각 꾸밈을 넣지 않는다. 제목·문단·번호 목록·표·코드블록만 쓴다.

## 5단계: 검증 안내

파일을 넘길 때 검증 절차를 함께 안내한다. 상세 항목은 `references/verification.md`에 있다. 요지는 이렇다.

- 새 대화에서 이 프롬프트만 붙여넣고 결과가 합격 기준을 만족하는지 본다.
- 변수를 다른 값으로 바꿔 한 번 더 돌린다.
- 가능하면 다른 AI 서비스에서도 한 번 돌린다.

검증은 사용자가 직접 하는 단계다. 이 스킬이 대신 통과를 선언하지 않는다. 같은 프롬프트라도 결과 문장은 매번 달라지므로, 기준은 "글자가 같은가"가 아니라 "형식과 요건을 지켰는가"로 잡도록 안내한다.

## 대화에 남길 말

파일을 만든 뒤 채팅에는 세 가지만 적는다. 프롬프트 전문을 채팅에 다시 풀지 않는다.

1. 어떤 작업을 대상으로 삼았는지 한 줄
2. 변수로 올린 값 목록
3. 로그에 근거가 없어 비워 둔 항목 (있을 때만)

3번이 특히 중요하다. 추측으로 채운 자리를 밝히지 않으면 사용자가 검증 없이 배포하게 된다.
